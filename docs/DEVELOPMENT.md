# 开发与维护

这是一款个人维护的离线工具，采用一条稳定主线加短期分支。无需建立复杂团队流程，也无需每次调整都安装手机包。

## 每次改动的固定顺序

1. **记需求。** 功能异常、数据纠错、功能建议分别用仓库 Issue 表单。写清楚现在的问题、希望怎么用、什么结果算完成；小文案修正可直接在 PR 中说明。
2. **开分支。** 从最新 `main` 建立 `fix/问题名`、`feat/功能名`、`data/数据主题` 或 `chore/维护主题`，一次只处理一件相关事情。
3. **修改和预览。** 运行 `npm start`，电脑直接看效果。涉及布局时检查正常桌面和约390px手机宽度；需要用户确认的体验在这一步确认。
4. **检查。** 运行下方命令；涉及资料时按 DATA.md 补来源。测试不通过就先修，不把失败写成“已完成”。
5. **提交 PR。** 默认先开 Draft PR，按现有模板写问题、结果、检查情况和未测部分；完成自查后再转为待审。自动检查为绿且人工看过后，以 Squash merge 合入 `main`。提交标题建议 `feat: …`、`fix: …`、`data: …`、`docs: …`、`chore: …`。
6. **按需发版。** 用户确认要发版、修复影响使用的问题，或积累了完整一组改动时构建 APK。记录实际完成的检查后创建固定版本标签与 Release，附安装包、SHA-256 和更新说明；已有安装包转正式发布时复用同一文件，不重打包。

这沿用 [GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)。`main` 表示可继续开发的稳定源码，正式发版由标签和 Release 标记；还没发版的内容写入 CHANGELOG 的 Unreleased。

## 本地最少命令

```sh
npm start
npm run check
npm test
python scripts/build_data.py --check
```

检查包括脚本语法、版本一致、离线资源完整、已跟踪文件中的私钥/令牌特征、词条覆盖与引用、档位规则、历史/收藏兼容和父级返回。测试用例中的固定数量属于当前数据基线，正式增加数据时应连同来源和预期数量一起审查，不能只为通过测试随意改断言。

`dist/` 是本项目真实网页源码，不是可以全部删除重建的普通前端输出目录。`dist/data.js` 单独由 `data/` 经 `python scripts/build_data.py` 生成；修改数据源后生成并一起提交，不手改生成结果。其他 HTML/CSS/JS 在此编辑。APK、签名、构建缓存和个人记录不进入源码提交。旧的 v0.3 手机网页 ZIP 脚本已停止继续打包；电脑预览和 Android 构建是当前维护入口。

## 版本号与发版

采用 `主版本.功能版本.修订号`：小问题修复如 0.4.1，成组新增功能如 0.5.0。公开接口或存档不兼容的大变化再考虑主版本升级。每次 APK 升级都要增加 Android `versionCode`；不得更换 `local.duye.nightreign` 包名和既有签名。

同时更新 `android/AndroidManifest.xml` 的 versionName/versionCode 与 `package.json` 的 version，补 CHANGELOG。数据快照版本在 `data/meta.json` 独立维护，不随纯界面更新虚增。网页缓存内容变化时更新 `dist/sw.js` 的 CACHE。

签名构建详见 [Android 构建](../android/README.md)。发布前需要：

- 检查 PR 自动检查、电脑与手机宽度预览。
- 公开发布 APK/ZIP 等附件前，逐项复核 [第三方来源与许可](../THIRD_PARTY_NOTICES.md) 中的分发权限；许可未确认的素材先取得明确许可或移除、替换，不能仅凭署名、源码公开或“非商业”说明视为可分发。
- 手机保留旧版记录，直接覆盖安装；确认收藏、水晶标记、设置仍在。
- 飞行模式冷启动，查询词条、夜王和地图；确认本地图片完整。
- 原记录→档位表→栏目→首页逐级返回；首页系统返回与页面返回均能退出。
- 清除最近查看并撤销；导出记录并在文件管理器确认 JSON 已保存。
- 核对 APK 的包名、版本、签名、SHA-256，填写实际设备/Android版本/结果。

测试结果写在 Release 说明或对应 PR 中即可，不另建重复台账。发布状态和测试状态分别记录：Draft 表示未公开，Prerelease 表示预发布，正式版本设为 Latest；正式发布不等于所有设备测试完成，未测项目仍如实保留。已发布 APK 不覆盖，不用同一个版本号发不同内容。

标签必须指向该 APK 实际构建使用的提交，不能仅取发版时 main 的最新提交。创建 Release 草稿，上传 `duye-handbook-v版本.apk` 和同名 `.sha256` 文件，重新下载核对文件大小及 SHA-256 后，再公开并设为 Latest；用 Releases API 的 latest 结果核实最终状态。不要将 APK 放进源代码提交。发布后发现内容需变更，使用新版本号和更高 versionCode。

v0.4.1 的标签固定在 `bc40b0680c5acd152be95099de08a9a0bc308c25`，沿用 2026-10-15 已交付 APK，2026-10-16 按维护者要求正式发布。后续文档和 CI 改动只进入 main/Unreleased；设备验收记录仍待补。

## 出问题怎么回退

优先撤销出问题的提交，在新分支上修复并重新验收。手机侧保留同一签名，以更高 versionCode 发布回退内容；不要强行降级或先卸载，避免丢失个人记录。源码可回退不等于手机存档迁移一定可逆，涉及存储结构时先导出记录，并测试旧存档兼容。

## 保管与仓库设置

`android/signing/` 存放现有私钥与密码，仅留本机，另在用户自己控制的加密备份中保留。不要把它发到 Issue、聊天、公开仓库或普通 ZIP。Git 忽略文件不是密钥备份；丢失密钥会影响覆盖升级。

每月审查依赖更新 PR；遇到游戏更新优先检查数据版本、来源差异和相关 Issue。每次发版检查签名备份可用，但不把备份内容放进仓库。先解决崩溃/数据错误，再做影响查询效率的体验，最后处理装饰。

## v0.5.0 界面和升级验收

`npm start`使用4317；独立预览用 `NIGHTREIGN_PORT=4318` 或双击启动脚本。预览的所有 localStorage 读写带独立前缀，Service Worker 仅清理自身前缀缓存。兼容测试使用合成旧收藏夹具，不访问真实正式版个人记录。

检查命令沿用 `npm run check`、`npm test`、`python scripts/build_data.py --check`；新增武器测试覆盖原始研究哈希、全部面板转录、未知和不适用、明确为零、旧传说效果关联、混合收藏、搜索组合和逐级返回。应用版本为0.5.0，数据快照为`2026.10.17-r1`。正式APK使用原来的无前缀存储键，兼容旧收藏、历史、水晶标记和设置；预览仍独立。

浏览器验收要实际覆盖桌面和 390px 窄屏、搜索和分类、详情、传说效果往返、刷新保留收藏、停止本地服务后的缓存重开。浏览器预览不等于安卓真机验收；预览已获用户确认，按v0.5.0执行PR合并、固定标签和签名APK发布。

新增目录/传说扩展使用显式输入，不修改三份用户研究原稿。倒计时状态也使用预览存储前缀；测试覆盖精确阶段边界、暂停/恢复、后台间隔、重载、校准和无负倒计时。渲染tick不重绘输入控件。

本轮浏览器验收已覆盖1280×900桌面、390×844窄屏、25件传说筛选、新增面板详情、空防御/异常隐藏、名称在前和末尾来源折叠；计时已验证开始、跨阶段、刷新继续、暂停后刷新、切换栏目、第二夜重置及非法校准提示。停止4318服务后重新加载，目录与计时仍可操作，随后已恢复服务。浏览器控制台未见本轮错误；尚未进行安卓真机测试。

后续发布目标为Android手机版App。界面改动优先以360–420px手机宽度验收；电脑默认390px框内预览，宽屏展开仅用于辅助检查。缩圈页面采用紧凑数字、四格时间轴与折叠校准区，避免大圆盘挤占手机首屏。

计时起点选择会暂停并设置本夜已过时间，用户点击开始后继续。测试覆盖11:00起点跳过前序阶段、选择后刷新、当前进度不重置、不同夜次和非法节点。

发布时以v0.4.1公开APK核对包名、签名与递增versionCode；GitHub Release中的标签、附件、SHA-256和实际构建提交必须一致。0.5.0不增加Android权限。

**E1 的查询流程。** 从词条详情进入“适用对象”，按魔法、祷告、战灰、角色技能、武器动作、道具分组；从目标对象进入“相关强化”反查已有词条。先显示适用部位与限制，来源报告放详情末尾。已经有详情的对象沿用原ID；尚无独立技能图鉴的魔法/战灰只补最小身份索引和关系详情，不顺带建完整伤害数据库。

E1验收必须覆盖：咆哮排除“荷莱露的撼地”；碎星大剑只涉及来源列出的动作段；自动辉剑仍为待核；隐士混合吐息只对应该组合而不是全部混合魔法；同名魔法与战灰不误合并。“强化咆哮与吐息”同时连接两个类别，12%/15%/20%继续从各场景原词条读取。正查、反查和武器关联使用同一份关系，不能各维护一套结果。
